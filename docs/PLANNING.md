> 状态：v1.0 · 需求已冻结 ｜ 2026-10-12
>
> **本文档只回答「做什么、给谁看、为什么」。**
> 不涉及技术选型、不涉及实现方式、不涉及部署方案。在需求没定下来之前讨论这些没有意义。

## 0. 为什么先写这份文档

上一轮从动手到上线把全套做完了，但视觉方向改了三次，最后整体删掉重来。

返工的根本原因不是执行出了问题，而是**「要一个什么样的博客」这件事从来没有被写下来过**。每次都是先有产出、再凭感觉判断对不对，于是每一轮都在为上一轮的假设买单。

这份文档的唯一目的：先把「做什么」钉死，让「怎么做」有据可依。

---

## 1. 一句话定位

一个面向国内读者的中文个人博客：技术笔记与生活随笔并置，作者是唯一的内容生产者。

---

## 2. 要解决的问题

| 问题 | 具体表现 |
|---|---|
| 内容没有归处 | 技术笔记散在本地文件、聊天记录、代码注释里；生活随笔根本没有载体 |
| 写作摩擦过高 | 每次想写都要先「折腾工具」。工具越强，越容易变成拖延的借口 |
| 需要一个对外身份 | 有一个可被引用的地址，比散落各处的片段更可信 |
| 需要长期可读 | 内容要能被三五年后的人（包括自己）读到，不能随某个平台一起消失 |

---

## 3. 读者

**只有一类读者**：中文技术圈的人，通过搜索引擎或社交分享进入，**很可能用手机打开**。

作者自己也是读者之一——这个博客同时充当长期笔记本。

**最典型的行为**：搜到一篇具体问题的解法 → 读完 → 关掉。少数人会留下来翻别的文章。

**由此推出的硬要求**：

- 手机上的阅读体验不能是「桌面版缩小」，必须单独考虑过
- 首屏要快，没人会为一个博客等三秒
- 单篇文章要在没有上下文的情况下也能读懂，不能假设读者看过前一篇
- 链接要能长期稳定分享

## 4. 内容

### 4.1 两种类型

| 类型 | 特征 | 频率预期 |
|---|---|---|
| **技术笔记** | 长、具体、有代码和结论，通常是解决某个问题后的复盘 | 低，且不规律 |
| **生活随笔** | 短、松散、可以没有结论，照片、读书、牢骚 | 更低，更随意 |

两类共享同一条时间线。**类型不占导航层级，用标签表达**（§13.1 于 2026-10-12 修订）：
写上「技术」或「随笔」标签即可，「只看技术」天然就是 /tags/技术/。

### 4.2 语言：只做中文（已决）

**全站中文，不提供英文版。**

曾经考虑过双语，理由是对外分享时更有用。否掉的原因：

- 双语让每篇文章的写作成本翻倍，而博客最大的风险是**断更**，不是「英文读者看不到」
- 双语会让信息结构、导航、每一条界面文案都变成两套，复杂度是全面的，不只是内容层
- 目标是「持续写下去」，不是「覆盖更多读者」。为了让少数英文读者方便，牺牲持续写作的概率，不划算

**推论**：不需要语言切换入口，不需要按语言分开的列表，不需要处理跨语言跳转。相关内容全部从需求中移除。

### 4.3 内容形态

**必须支持**：标题、摘要、正文、代码块、图片、链接、列表、引用、表格。

**可能需要**：数学公式、系列连载、长文目录、图片相册。

## 5. 功能需求

按「没有它会怎样」排序，不按实现难度。

### 5.1 必需

| 能力 | 没有它会怎样 |
|---|---|
| **写作与发布足够省事** | 每次想写都要先折腾工具，最终不写。这是上一轮确认过的痛点。**写作入口用现成工具（网页或本地均可），但不自建编辑器**（见 §9.1） |
| **中文排版舒适** | 断行、标点、行高处理不好，读者读两段就走 |
| **手机可读** | 大部分读者在手机上，体验差等于没有读者 |
| **按时间浏览** | 最基本的导航，没有就没法「随便翻翻」 |
| **单篇稳定链接** | 分享、被引用、被搜索引擎收录的前提 |
| **订阅** | 让愿意追更的人不必反复来刷 |
| **标签或分类** | 预期长期多量，这是内容变多后唯一的组织手段 |
| **归档页** | 同上，按时间倒查的入口 |
| **列表分页或分段** | 数百篇不能全塞进一页 |
| **站内搜索** | 数百篇之后，搜索是找回旧文的唯一可靠方式，也是读者从站外进来后继续停留的理由 |

### 5.2 重要但不致命

| 能力 | 价值 |
|---|---|
| 系列连载 | 成体系的技术文章需要「上一篇 / 下一篇」 |
| 关于页 | 告诉读者你是谁、这个博客为什么存在 |
| 相关文章 | 多量之后，帮助读者在文章之间流动 |

### 5.3 可选

| 能力 | 状态 |
|---|---|
| **访问统计** | **已定：只做服务端本来就可见的部分**，见下方「统计口径」 |
| **深色 / 浅色主题** | **已定：两套都做，深色自动跟随系统**，配色见 §10.7 |
| **图片相册** | 未定。生活内容可能需要，但会明显增加存储与管理成本 |

#### 统计口径

**只统计服务端本身就能看到的信息。读者不参与，也不被识别。**

| 要看的 | 说明 |
|---|---|
| 每页访问量 | 按文章与页面聚合 |
| 来源 | 搜索引擎 / 直接访问 / 外部链接 |
| 地区 | 粗粒度，不精确到个人 |
| 设备 | 桌面 / 手机，用来验证移动端投入是否值得 |
| 时间分布 | 什么时候有人看，用来决定发布时间 |

**硬约束**

- **零客户端参与**：不加载任何统计脚本
- 不使用 Cookie，不做跨站追踪，不识别个人
- 不公开展示阅读量（见 §7）
- 指标应读作「哪篇被看得多」，**不是「有多少读者」**——同一个人刷新三次会算三次
- 需过滤已知爬虫，否则数字会被抓取流量推高 |

## 6. 质量要求

这些不是「最好有」，是**验收标准**。

| 维度 | 标准 |
|---|---|
| **速度** | 国内直连首屏 1 秒内可见内容；不为任何第三方资源等待 |
| **可达性** | 禁用 JavaScript 后仍能完整阅读；键盘能完成所有导航；屏幕阅读器可用 |
| **隐私** | 默认不收集读者数据；不用第三方追踪；不做 Cookie 同意横幅——因为根本没有 Cookie |
| **可迁移** | 内容以纯文本形式存在，随时能整体搬走；不锁死在某个平台或数据库里 |
| **自主** | **站点与内容的可用性不依赖任何第三方服务**；第三方涨价、改规则或消失时，站点照常运行 |
| **可维护** | 作者不写代码时站点也能稳定运行；依赖越少越好，因为没人会定期升级它们。注：自建 + 百篇量级仍会带来持续维护成本，但舍弃手机写作后，这一代价已明显低于三者叠加时 |
| **可恢复** | 误删误改能回退；内容有独立于运行环境的备份 |

### 6.1 备份与恢复

**静态站点本身不必备份**——它随时可以从源码仓库重新生成。所以真正需要备份的只有一样：**源码仓库**（代码加全部正文）。

| 项 | 决定 |
|---|---|
| 备份对象 | 源码仓库（含全部 Markdown 正文） |
| 副本 | 三份：GitHub 远端、本地工作副本、**本地离线归档**（打包文件，不依赖任何 Git 服务） |
| 离线归档频率 | 每次发布后一次；不发布时至少每月一次 |
| **验证** | **每季度从离线归档完整还原一次**到临时目录，确认能正常生成站点 |
| 记录 | 每次验证在仓库里留一行（日期加结果），避免事后「以为验证过」 |

**原则：未经验证的备份不算备份。** 只打包不还原，等于把风险从「可能丢数据」换成「以为不会丢数据」——后者更危险，因为它会让人放弃其他防备。

## 7. 明确不做

写下来，是为了将来拒绝它们时有据可依。

- **不做评论（已决）**：需要有人长期处理垃圾评论，是一笔持续负担；作者不常回复反而显得冷清。**没有互动机制，也就没有需要 moderation 的东西**
- **不做多语言**：只做中文，理由见 §4.2
- **不把站点托管在第三方平台**：不以 Notion / Substack / Medium 之类作为内容源，站点构建与发布都在自己的机器上。**代码仓库托管到 GitHub 是允许的**（见 §9.1），但 GitHub 只作为源码存放与同步，不承担站点运行。**正文与代码同仓存放，不拆分**——已确认正文随仓库进入 GitHub 是可接受的
- **不做社区**：没有用户系统、没有关注、没有私信
- **不做推荐算法**：读者的时间该花在内容上，不是被留住
- **不做广告与联盟链接**
- **不公开展示阅读量**：会引向攀比，还需要额外请求
- **不做登录才能阅读**
- **不追求全平台覆盖**：不做小程序、不做 App
- **不为技术而技术**：只在简历上有价值的复杂度，一律不加

## 8. 分期

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| **一、能用** | 写作与发布、中文排版、深浅两套配色、手机可读、按时间浏览、单篇链接 | **发出第一篇文章** |
| — | 组织方式（链接规则、标签体系、归档结构、分页行为）在阶段一即已定死，见 §13 | |
| **二、好找** | 标签、归档、分页、订阅、关于页 | 文章能被分类找到 |
| **三、好用** | 站内搜索、系列、图片、相关文章 | 作者愿意持续写，读者愿意留下来翻 |
| **四、锦上添花** | 访问统计（口径见 §5.3） | 只在前面都稳定之后才考虑 |

**「一」没跑通之前不碰「三」。** 上一轮的教训正是先做了「四」，才回头发现「一」还不成立。

**因为预期长期多量，阶段一就必须把组织方式定死**：链接规则、标签体系、归档结构、分页行为。这些后补的代价远高于一开始就想清楚——每一篇已发布的文章都是一个需要迁移的存量。

## 10. 视觉方向：如何决定

已决定**不先定方向，而是先看样例再选**。这一节规定怎么选。

### 10.1 为什么要走这一步

视觉方向已经反复过三次（终端风 → 个人主页风 → 极简文字风），每次都是做完才发现不对。凭文字描述判断视觉，本来就不靠谱——「极简」和「冷淡」在描述里几乎一样，做出来差别很大。

### 10.2 做法

用**同一组内容**（同样的首页文案、同样的三篇文章、同样的列表数据）产出若干样例，只换视觉方向。这样对比的变量只有一个。

每个样例至少覆盖四个画面：

- 首页（列表形态）
- 文章详情（正文排版、代码块、图片）
- 手机视图
- 深浅两种配色

### 10.3 评审标准

**不是「哪个好看」，而是「哪个更符合 §3 的读者和 §6 的质量要求」。** 具体问四个问题：

1. 一个搜到技术文章、用手机打开的人，能不能立刻开始读？
2. 中文正文读起来累不累？
3. 它是否暗示了「这里会有新东西」——还是看起来像废弃了很久？
4. 三年后回看，会不会觉得土？

### 10.4 方向选定：C · 杂志排版

在 A–E 中选定 **C（杂志排版）**：大标题、宽松留白、图片主导。

**这个方向有一个必须先解决的矛盾**：杂志排版的典型形态依赖图片，而本站内容以技术长文为主——正文里通常是代码块和截图，很可能整篇文章都找不到一张合适的封面图。

所以 C 不能照搬杂志网站的图片流做法。真正要验证的是：**在「大部分文章没有封面图」的前提下，这个方向还成不成立。**

### 10.5 C 的两个变体

| 变体 | 做法 | 前提 |
|---|---|---|
| **C1 · 图片主导** | 首页顶部一张大幅主视觉，文章以带封面的卡片呈现 | 需要作者持续产出或挑选配图 |
| **C2 · 排版主导** | 完全不用图，靠字号对比、留白与细线做出杂志感 | 纯文字也成立，但视觉冲击力弱 |

两个变体用**同一组内容**呈现，直接对比「有图」与「无图」的实际观感。

### 10.6 评审记录（2026-10-12）

**已产出**：samples/ 下四个自包含页面（C1 首页与文章、C2 首页与文章），均覆盖桌面、手机、深浅配色。

**C1 · 图片主导**

- 首页：主视觉占掉首屏约 45%，冲击力确实全部来自它
- 文章页：21:9 的封面把标题推到首屏之下。**从搜索引擎直接落到文章的人，第一眼看到的是一张图，不是他在找的答案**
- 硬成本：每篇都要一张封面。技术文章（修一个 bug、读一段源码）通常没有天然合适的配图，只能凑——**而凑出来的图比没有图更糟**

**C2 · 排版主导**

- 首页：成立。大报头 + 衬线标题 + 细分隔线，看得出是被认真设计过的，不是「没做完」
- 文章页：首字下沉、行宽、代码块都舒服，**完全不需要图**
- 弱点：文章之间缺视觉区分，到五十篇时列表会显得单调；手机端会退化成「一个还算好看的普通列表」

**由观察得出的建议**

C1 的封面是**每篇都要付的成本**，C2 什么都不要求。建议以 **C2 为底，把 C1 的封面处理当作可选项**：有合适配图的文章享用大幅主视觉，没有的就不放，不为凑图而放图。

### 10.7 定稿规格

**结论：以 C2（排版主导）打底，封面图作为可选增强。**

## 12. 写作流程

需求已冻结，这是第一个落地的设计决定——它决定内容怎么存放、怎么发布，其余选择都受它牵引。

### 12.1 出发点

§5.1 要求「写作与发布足够省事」，痛点很明确：**上一轮做完了全部功能，文章数是零。**

已决定**不自建编辑器，改用现成工具**（§9.1）。所以这一节定义的不是「编辑器长什么样」，而是**写作入口与内容存放的约束**——工具可以换，约束不能破。

判断标准只有一条：

> **从「想写」到「写出来」之间需要几个动作？** 越少越好。任何需要翻文档、查格式、复制路径的步骤，都是在为「不写」提供借口。

### 12.2 一篇文章的生命周期

| 阶段 | 要求 |
|---|---|
| **起念** | 文章有固定的存放位置；新建一篇时元数据骨架自动带出，不必翻文档查格式 |
| **起草** | 未完成的文章**不会被发布出去**，也不出现在列表、搜索、订阅里 |
| **预览** | 发布前能看到接近真实的渲染效果，尤其是代码块、图片、公式 |
| **发布** | 一次操作完成（提交并推送），生成与部署自动跟上 |
| **修改** | 改错别字是一等公民——改完即生效，不必重走流程 |
| **撤回** | 能下架文章，且下架后旧链接给出明确提示，而不是死链 |

### 12.3 元数据怎么填

一篇文章涉及：标题、摘要、日期、类型、标签、封面、系列。

**原则：能推导的不问，能默认的不填。**

| 字段 | 来源 |
|---|---|
| 标题 | 必填 |
| 日期 | 默认取发布时刻，可改（补写旧文时需要） |
| 类型 | 必选，但只有技术 / 随笔两个选项 |
| 摘要 | 可留空；留空时从正文首段截取 |
| 标签 | 可选，但必须能**复用已有标签**——否则到百篇量级时「rust」和「Rust」会变成两个标签 |
| 封面 | 可选，见 §10.7 |
| 系列 | 可选 |

**不引入的字段**：作者、语言、阅读量、任何需要作者手工维护的编号或状态位。

### 12.4 图片

封面与正文配图都以文件形式放进仓库。要求：

- **不需要手工拼接引用路径**——由编辑器补全或由脚本生成
- 图片进入 §6.1 的备份范围（否则备份是不完整的）
- 能找出并清理不再被引用的图片，且不会误删仍在使用的
- 图片体积受控，否则仓库会随文章数一起膨胀——百篇量级下这一点不可忽略

### 12.5 两个入口必须共用一份内容

写作有两个入口，**都用现成工具，不自建**：

| 入口 | 适用场景 |
|---|---|
| 网页编辑器 | 快速起草、临时起意、改错别字 |
| 本地编辑器 | 长文、需要反复查资料、需要版本管理 |

**硬约束——这是选用任何现成工具的前提：**

1. 两个入口操作的必须是**同一份内容**。不允许「网页里写的」和「本地写的」分两套管理，那等于把 §5.1 的痛点换个形式还回来
2. 内容的最终存放位置由本项目掌握，**不锁死在工具里**（§7）。工具换了，内容不用搬家
3. 图片必须进入 §6.1 的备份范围

**优先级：如果找不到同时满足三条的现成工具，宁可只保留本地入口**，也不要为了多一个入口而牺牲内容的所有权。

### 12.6 现成方案的核对结果（2026-10-12）

按 §13 第 1 步核对了市面方案。**结论：三条硬约束可以被满足**，但不同方案付出的代价差别很大。

| 方案 | 同一份内容 | 不锁死 | 图片进备份 | 是否需要自建 | 核实到的事实 |
|---|---|---|---|---|---|
| **GitHub 自带的网页编辑器 / github.dev** | ✓ 直接编辑仓库 | ✓ | ✓ | **不需要** | 官方文档确认：浏览器里的 VS Code，**免费**，可编辑文件并提交 |
| **Keystatic** | ✓ | ✓ | ✓ | **需要** | 要注册 GitHub App（clientId、clientSecret、回调地址）、配置密钥环境变量，并有一个常驻服务；**官方「部署」文档至今标着 Coming soon**。另：它依赖 React |
| **Decap / Sveltia** | ✓ | ✓ | ✓ | 需要一个 OAuth 后端 | 后端通常放在第三方平台上，与 §7 有张力；且编辑器需要直连 GitHub |

**结论**

- **零自建就能满足全部三条约束的是 GitHub 自带的网页编辑器**（含 github.dev）。它天然满足——**因为它编辑的就是仓库本身**
- 其余方案在内容层面同样满足三条约束，但都要额外交付：Keystatic 要注册 GitHub App 并保管密钥，Decap 系要把 OAuth 后端推给第三方

**因此 §12.5 那条优先级不需要启用**——存在零成本满足全部约束的方案，不必为了多一个入口而牺牲内容所有权。

**已确定：网页入口使用 GitHub 自带的编辑器**（含 github.dev）。它与本地编辑器操作的是同一个仓库，因此天然满足 §12.5 的三条约束，且不需要任何自建。

### 12.7 发布

- **一次操作**：提交并推送，其余（生成、部署）自动完成
- **可回退**：发布出问题能退回上一个状态，且回退本身也是一次操作，不是手工抢救
- **失败必须可见**：见 §12.8

### 12.8 失败必须可见

发布失败、图片缺失、生成失败——**都要明确告诉作者，不能静默失败。**

这条来自真实教训：上一轮有一次构建其实失败了，但输出里出现了「Complete」字样，看起来像成功，导致连续几次部署都没生效而无人察觉。**判断成功要看退出状态，不是看输出里有没有好看的字。**

### 12.9 明确不做

- **不自建编辑器**：网页和本地都不自建，用现成的（§9.1）
- **不做协作、评论、版本对比界面**：单人博客不需要
- **不做定时发布**：用不到，而且会引入一个必须常驻的调度——多一个会坏的东西
- **不要求手机写作**：§9.1 已舍弃

## 13. 内容模型与链接规则

§8 要求阶段一就把组织方式定死，理由是「每一篇已发布的文章都是一个需要迁移的存量」。这一节补上那块空白。

> **状态**：§13.1–13.6 **已全部确定**（2026-10-12）。这一节的内容一旦发出第一篇文章就会变成存量，之后只增不改。

### 13.1 链接规则（2026-10-12 修订：统一前缀）

**硬规则：一旦发布，链接永不改变。** 改链接意味着所有已分享的地址、搜索结果、外部引用全部失效。

**修订内容：原来的 /posts/ 与 /notes/ 双前缀合并为 /articles/。**

修订前的规则是「类型决定前缀」，因此派生出一条别扭的约束——**发布后不能改类型**，因为改类型会改链接。把类型降为标签之后，这条约束随之消失：类型现在可以随时改，不影响任何链接。

**现在的规则：**

    /articles/<目录名>/

目录名即链接末段——**命名目录本来就是写作时必须做的动作**，所以这不额外增加步骤，符合 §12.1 的「减少动作」。

**由「链接永不改变」推出的唯一一条硬规则：**

> **发布之后不要改目录名。** 目录名就是链接，改名等于让所有已分享的地址失效。

只在「文章尚未发布」时才能自由调整。

目录名建议用英文短横线格式（rust-bedrock-renderer）。**中文目录名也允许**，但链接会变长、分享时会被百分号编码，不推荐。

**为什么当时选了这个方案**：链接里带语义对分享和收藏有价值；日期路径（/2026/10/12/）虽然零思考但看不出内容，中文标题直接入链则会被编码成一长串百分号。

### 13.2 每篇文章是一个目录

    content/articles/
      rust-bedrock-renderer/
        index.md          ← 正文与元数据
        cover.jpg         ← 封面（可选）
        render-chart.png  ← 正文配图

**为什么用目录而不是单文件**：§12.4 要求「能清理不再引用的图片」。图片与文章放在一起，删文章时一起删，不会留下孤儿文件；反过来也能一眼看出某篇文章用了哪些图。

### 13.3 草稿

元数据标 draft: true 的文章**不生成页面**，也不出现在列表、归档、标签、搜索、订阅里。改为 false 即发布。

### 13.4 标签规范化

§12.3 要求能复用已有标签，避免「rust」和「Rust」变成两个。

**做法：仓库里维护一份标签清单，写作时从中选。** 新增标签需要显式加进清单——这一点摩擦是有意的，因为**标签一旦分裂，合并成本随文章数增长**。

### 13.5 分页

| 位置 | 每页 | 说明 |
|---|---|---|
| 首页 / 列表页 | 20 篇 | 百篇量级下约 5 页 |
| 归档 | **不分页** | 它是用来扫的；一百来行可以一次滚完，分页反而破坏「一眼看全」 |
| 标签页 | 不分页 | 单个标签天然不会太多 |
| 搜索结果 | 不分页 | 按相关性排序，取前若干条 |

### 13.6 元数据定稿

| 字段 | 必填 | 说明 |
|---|---|---|
| title | ✓ | |
| date | ✓ | 默认当前时刻，可改 |
| description | | 留空时从正文首段截取（§12.3） |
| tags | | 从 §13.4 的清单里选。**体裁用「技术」/「随笔」两个保留标签表达**，见 §13.1 |
| cover | | 文件放在文章目录里（§13.2） |
| series | | 可选 |
| draft | | 默认 false |

**不引入的字段**：作者、语言、阅读量、序号、任何需要手工维护的状态位（§12.3）。

## 14. 生成、托管与部署

### 14.1 先分清架构与工具

**架构**由需求推导，几乎没有选择余地；**工具**是同一架构下的多个实现。

先把架构定死，工具才有评判标准。否则就会像上一轮那样——从「装哪个主题」开始，做到最后才发现方向不对。

### 14.2 架构：静态生成

| 需求（出处） | 推出的约束 |
|---|---|
| 站点自建，不依赖第三方（§7） | 页面必须从自己的服务器发出 |
| 禁用 JavaScript 后仍能完整阅读（§6） | **不能是客户端渲染的应用**——内容必须在 HTML 里 |
| 国内首屏 1 秒内（§6） | 不能有阻塞的第三方资源，不能依赖外部接口 |
| 无 Cookie、不收集读者数据（§6） | 不做需要会话的服务端逻辑 |
| 百篇量级 + 归档 / 标签 / 分页（§5.1） | 需要构建期的全站视图 |
| 内容存在 Git 仓库（§13） | 从仓库生成 |
| 发布即推送（§12.6） | 生成由推送触发 |

**结论：静态生成。** 推送时一次性把页面生成成 HTML，服务器只负责发文件——没有运行时、没有数据库、没有会话。

这不是偏好，是逐条推出来的：只要「无 JS 可读」和「无 Cookie」这两条还在，服务端渲染就没有必要；而静态方案同时把速度、可维护性、隐私三条一起满足了。

### 14.3 部署：推送即发布

    本地编辑器 / GitHub 网页编辑
              ↓ 推送
        Git 仓库（GitHub）
              ↓ 触发
            生成页面
              ↓
       自己的服务器（只发文件）

要求（来自 §12.6、§12.7）：

- 推送后自动完成，不需要手工搬运产物
- **失败必须可见**——上一轮的教训正是构建失败了、输出看着却像成功
- 可回退：退回上一个状态是一次操作，不是手工抢救

### 14.4 搜索：已定用客户端查询

静态站在「读者不能依赖 JavaScript」这一条上，搜索是唯一麻烦的地方。已定：

> **§6 的「完整阅读」指内容可读，不指功能可用。**

因此搜索可以用客户端方案——**所有文章在禁用 JavaScript 时完全可读**，只是搜索框用不了。

| 方向 | 决定 |
|---|---|
| **A · 客户端查询** | **已定**：生成时把索引做成文件，浏览器加载后查询 |
| B · 服务端查询 | 不采用——**为搜索单独引入一个常驻服务不划算** |

**由这个解释推出的两条要求：**

1. 搜索页在禁用 JavaScript 时**必须明确说明并指路**（指向归档与标签），不能是一片空白或一直转圈。样例见 samples/search.html
2. **搜索索引不能拖慢正常阅读**——它只应在进入搜索时才加载，不该出现在文章页里

### 14.7 部署现状（2026-10-12 实测）

**服务器上 80/443 已被另一个项目占用。** `~/nefu-pa-web` 的 caddy 容器发布着这两个端口，
服务 `nefupa.intzot.asia`（东北林业大学匹克球协会）。所以博客不能自带 web server 抢端口，
只能接入那个 caddy。

**已完成的准备**（不依赖 nefu 做任何改动）：

| 项 | 内容 |
|---|---|
| 产物位置 | /srv/intzot.asia/releases/时间戳/，以及 current 软链 |
| 发布方式 | scripts/deploy.sh：本地构建 → rsync → 原子切换软链 → 保留 5 个版本 |
| 权限 | 目录 755、文件 644，保证容器内进程可读 |
| 接入配置 | 写好了 deploy/caddy.intzot.asia.conf，**尚未应用** |

**证书不需要备案（2026-10-12 实测确认）。**

http://intzot.asia 从国内访问会被阿里云以「未备案」拦截（403），但证书照样签下来了。
实际用的是 **http-01** 挑战，不是 tls-alpn-01——这一点我一开始推断错了，日志纠正了它。

原因是：**备案拦截只作用于国内来源的流量**。Let's Encrypt 的校验服务器在国外，
它的请求直接落到这台机器上，所以 http-01 能通过。**推论：续期也会成功。**

不要为了「先让国内 HTTP 能通」去改配置——那解决不了备案问题，反而可能弄坏签发。

### 14.5 工具选型的评判标准

架构定了之后，工具的选择标准就是 §14.2 那张表——**任何候选工具，只要违反其中一条就出局**。

### 14.6 工具选型（2026-10-12）

#### 先淘汰

| 候选 | 淘汰理由 |
|---|---|
| **Next.js / Nuxt** | 它们是**应用框架**，默认客户端渲染。「无 JS 可读」在它们那里需要持续对抗框架默认值才能维持——§6 是硬约束，不适合建立在「必须一直小心」的基础上 |
| **Jekyll** | Ruby 工具链，构建慢，百篇量级下代价明显；生态偏老式博客主题 |
| **Hugo** | 单二进制、构建最快，**这两点确实吸引人**；但模板是 Go template，对 §10.7 这种精细排版表达力偏弱，且引入一门作者不熟的语言 |
| **Hexo** | 可用，但主题生态以另一种美学为主，自定义成本高；公式与自定义布局的支持不如组件化方案 |

#### 入选：Astro

| 约束（§14.2） | Astro 的对应 |
|---|---|
| 构建期生成，**零 JS 是默认** | 官方明示：Zero JS, by default |
| 从 Markdown + Git 生成 | 原生支持 |
| 构建期全站视图（归档 / 标签 / 分页） | 原生支持 |
| 精细排版控制 | 组件模型 + 作用域样式，对 §10.7 友好 |
| **元数据校验** | 内容集合自带 schema 校验——**正好对应 §13.6 定稿的八个字段**，填错在构建时报错，而不是发布后才发现 |
| 作者背景 | TypeScript，与作者已有技术栈一致 |

#### 关于「上一轮用的就是它」

上一轮的 Astro 项目被删了。这里要分清两件事：

> **删掉的原因是「要一个什么样的博客」从来没有定下来，不是生成器选错了。**

需求定稿之后重新筛，它仍然是最贴合的那一个。**这个结论是被筛出来的，不是惯性。**

#### 两个必须记住的坑（都已在实现中真实踩到）

**一、构建可能「看起来成功，但退出码非零」**

上一轮真实发生过：前一步成功并打印了完成字样，后续步骤失败，**整条流水线看起来是成功的**，导致连续几次部署没生效而无人察觉。

选了 Astro 之后，**同一个坑又出现了一次**：图像优化因为缺 sharp 而失败，Astro 先打印了 Complete，最后以退出码 1 结束——构建脚本里的 and 因此静默跳过了搜索索引的生成。表象完全一样：输出里有「Complete」，但东西没生成。

**结论：部署环节必须显式检查退出状态（§12.7）。**

**二、pnpm 在 sharp 上会写出断掉的软链**

sharp 声明了可选的 peer 依赖 @types/node，pnpm 把它的实际目录建成：

    .pnpm/sharp@0.35.5_@types+node@24.19.2/node_modules/sharp

但顶层软链写成了：

    node_modules/sharp -> .pnpm/sharp@0.35.5/node_modules/sharp

少了后缀，链是断的。后果是 Astro 报 MissingSharp，**图像优化整体失效**，并连带触发上面那条退出码问题。

已在 pnpm-workspace.yaml 里用 nodeLinker: hoisted 绕开（本项目是应用而不是要发布的库，扁平布局没有副作用）。

**注意：pnpm 10+ 把 nodeLinker 这类配置从 .npmrc 挪到了 pnpm-workspace.yaml，写在 .npmrc 里不生效**——这一点也实测确认过。
